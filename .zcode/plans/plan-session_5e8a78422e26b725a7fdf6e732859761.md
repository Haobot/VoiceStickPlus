# 音频质量评估与双音源 A/B 对比实验台

## Context

识别精度排查已确认瓶颈在音频链路 + 模型能力。现在有两个音源（小米遥控器网关中继 / StickS3 自带麦），但判断某次音频好坏只能靠听 ogg 和翻日志——需要一套**直观可视的评价标准**：波形/频谱可视化、指标红绿灯、双音源并排对比与同步试听（左右耳分源）。

探索确认的关键事实：
- DebugAudio 保存的就是喂 ASR 的最终 ogg，但**网关中继与 Stick 麦在文件名上无法区分**（都是 `VS-` 前缀）；
- **无需改固件/协议即可自动标注来源**：网关模式下遥控器语音键以 `"source":"xiaomi"` 的 primary 按键事件到达桌面端（`StateEvent.source` 已解析），只是 `handleButtonDown`（VoiceStickCoordinator.swift:959）没把它传进会话创建；
- `spectrogram_server.py`（625 行，纯标准库）已有频谱图/波形/播放/缩放单会话视图，是现成骨架；健康阈值已有既往实测数据（2026-10-16 取证：频段占比、帧比例指纹、RNNoise 判据）可锚定红绿灯。

用户未答问卷，按推荐执行：**分两期**（第一期零固件；真同事件双录固件改造列第二期）+ **本地网页工具**形态。新分支 `feat/audio-quality-lab`。

## 评价标准（三层指标，全部做成红绿灯）

| 层 | 指标 | 健康判据（既往取证锚定） |
|---|---|---|
| 传输完整性（侧车数据） | 帧覆盖率 = frames×40ms÷音频时长；seq 缺口实测丢帧数；span/recording | 覆盖率≈1.0 健康；恒 0.5~0.8 = 设备端尾帧丢弃指纹；span≫说话时长 = BLE 积压 |
| 信号质量（PCM 计算） | peak/RMS dBFS、削波率、DC；底噪 RMS（首尾静音窗）+ SNR 估计；五档频段能量占比（<300/300-2k/2-4k/4-6.5k/>6.5k）；F0 中位数+轨迹（自相关）；能量 VAD 分段 | 频段：<300Hz 20~31%（异常 45%）、4-6.5k 15.5~21.4%（异常 8~13%，"发闷"指纹）；双源 F0 比值≈伸缩比（1.094 案例） |
| 后处理效果（A/B 模式） | ΔRMS、Δ底噪、Δ频段占比对照表 + 双波形/双频谱并排差值；现场 ASR 识别文本（最终锚点，来自侧车） | RNNoise 判据：语音 RMS 变化 ≤0.3dB 且底噪下降；AGC 判据：RMS 落入目标区间 |

标准全文落 `Doc/Ref/audio-quality-metrics.md`（定义+阈值+取证出处）。

## Phase 1 实施（本分支全做，零固件/协议改动）

### 1. macOS 配套（让工具有好数据）

- **会话来源自动标注**：`event.source` 从 `handleButtonDown`/c2t 启动 click/字幕路径下传进会话创建；前缀判定抽纯函数（对齐 ProviderPopupMapping 模式，放 VoiceStickCore 便于单测）：设备为遥控器直连 → `RC-`；Stick 设备 + source=="xiaomi" → `VG-`（网关中继）；否则 `VS-`。改 `VoiceStickCoordinator.swift`（:959、:1531、:1751、`deviceNamePrefix` :3700）与 `DebugAudioRecorder.swift`。
- **会话侧车 `<同名>.json`**：`finish()` 时写（source、deviceClass、sessionID、frames/span/recording、noiseSuppression、seqGap）；ASR onFinal 后补写 `finalText`。
- **seq 缺口丢帧实测**：`handleAudioFrame`（:1604）按 `frame.seq`（已解析未用）累计缺口，新 `AudioSeqGapTracker` 纯逻辑结构进 Core + 单测。
- **增强开启时双份保存**：`audio_noise_suppression=on` 时协调器在增强**前**另挂一路 mux+recorder，落 `<名>.raw.ogg`——后处理前后对比有真数据。
- Windows 侧同构（debug_audio_recorder.cc 注释"对齐 macOS"）**登记 backlog 不动**；工具对无侧车/旧前缀文件容错显示。

### 2. 工具 `scripts/e2e_test/audio_lab.py`（新脚本，原 spectrogram_server.py 不动）

复用其 FFT/STFT/绘制/播放骨架与双平台目录探测，新增：
- 会话列表带侧车列（来源/时长/丢帧/识别文本摘要）；
- 单会话视图 = 现有能力 + 指标面板红绿灯；
- **A/B 视图**：任选两文件 → 包络互相关自动对齐 + ±10ms 手动微调、双波形同轴叠放、双频谱并排、指标对照+Δ 表、等响度开关（RMS 归一）；
- **播放三模式**：左右耳分源同步（左=A 右=B，直接实现"同时播放两个音源"）、即时切换（空格 swap）、单放；循环开关；
- 指标全部浏览器 JS 计算（F0 自相关新写 ~60 行）；Chrome/Edge 主用，Safari ogg 解码失败时页面提示。

### 3. 测试与验收

- `swift build` + `swift run VoiceStickTests` 全绿；新增单测：前缀三态映射、seq gap 统计、侧车序列化、raw 双保存（假帧 fixture）。
- 真机验收（`open` 启动 app）：T1 Stick 麦会话 → `VS-`；T2 遥控器网关会话 → `VG-` + 侧车 source=xiaomi + finalText；T3 遥控器直连 → `RC-`；T4 开增强 → `.ogg`+`.raw.ogg` 成对；T5 audio_lab 双文件对比 + 左右耳同步播 + 微调对齐；T6 红绿灯与既往健康/异常样本口径对拍（用 scripts/e2e_test/corpus/*.ogg 与历史 DebugAudio 文件）。

## Phase 2（真同事件双录——验收 Phase 1 后另起，本期不做）

固件在 EXTERNAL 会话可选并行采集 Stick 麦（audio_pipeline.c 加第二采集任务 + PSRAM 环，60s≈1.9MB/8MB 余量充足），会话结束经 audio_tx 以 flags bit2 调试流标记导出（Opus 后 ~120KB/30s），macOS 写成 `*-micref.ogg` 自动配对进 audio_lab。协议 flags 新 bit 向后兼容零版本变更（byte12 bit2+ 空闲，Windows 只测 bit0/bit1），须 protocol.md+固件+macOS 同步并过真机 OTA/功耗回归（跨版本契约红线）。

## 风险

- 复述配对（说两遍）混入说话本身差异——UI 明示"顺序复述模式"，Phase 2 消除；
- VG- 前缀 macOS 先行造成双端命名暂不同步——backlog 登记，工具按前缀容错；
- 侧车 finalText 依赖 ASR 回调时序（取消会话无文本）——字段可缺失，工具显示"—"。

工作量估计：Phase 1 ≈ 2~3 天（macOS 改动 0.5~1 天、工具 JS 1~1.5 天、文档+测试 0.5 天）。
