# 工作总结、经验沉淀和教训反思

把一次工作中的结论沉淀为可检索、可溯源的仓库文档。核心原则：**先查再写、能追加不新建、证据导向、同步到位**。

## 三种场景与落点

| 场景 | 落点 |
|---|---|
| 教训/经验（排查结论、坑、根因） | `Doc/Expe/` 单篇文档 |
| 阶段工作总结（一次任务的方案与结果） | 有设计价值 → `Doc/Plan/`；纯结论 → 追加到相关 `Doc/Expe/` 文末尾 |
| 高频坑 / 操作红线（每次任务都要遵守） | 升级到根 `AGENTS.md`「给 Agent 的提示」（一行浓缩），细节仍放 `Doc/Expe/` |

Hub（AGENTS.md/CLAUDE.md/CODEBUDDY.md）只收红线级一行浓缩 + 索引指针，细节一律进 `Doc/` 子目录——遵循仓库 Hub-and-Spoke 架构。

## 流程

1. **先查**：`ls Doc/Expe/` + grep 关键词，读 `claude-memory-distilled.md` 相关章节。判断是同主题变体还是全新主题。
2. **追加 or 新建**：已知根因的新变体 → 在旧文末尾追加新节（保留被推翻的旧结论，如"二轮优化"先例）；独立新场景 → 新建文件 + 与同主题旧文互链。
3. **写文档**：按下述命名与结构约定。
4. **同步**（见下节清单），缺一不可。

## 命名与结构约定

- 文件名：全小写、连字符分词的英文主题短语 + **必须**带日期后缀 `-YYYY-MM-DD`（修复/结论完成日）。例：`ble-watcher-silent-death-pairing-stuck.md`、`website-flasher-cors-failed-fetch-2026-08-10.md`。
- 标题：`# <一句话症状/主题>`。
- 开头元信息块：日期、相关文件路径、相关 commit 短哈希。
- 正文骨架：**症状 → 日志判据 → 根因 → 修复（机制 + 常量值 + commit）→ 验证 → 长期技术记忆/经验 → 遗留/观察项**。最完整模板参考 `Doc/Expe/ble-stale-session-reconnect-deadlock-2026-07-17.md`。
- 「判据」式写法：教人下次用日志特征快速识别同类问题（如"`polls=0` 是典型僵尸链路"），而不只记录本次修复。

## 同步清单

1. `Doc/Expe/claude-memory-distilled.md`：相关章节增补条目 + §10 高频速查清单追加一行（一句话症状判据 + 新文链接）。
2. 同主题旧文：互链。
3. 有配套方案文档 → 放 `Doc/Plan/` 并在 Expe 文中引用。
4. 触及模块描述漂移 → 核对 `Doc/Agent/` 对应主题文档。
5. 升级为红线/高频坑 → 根 `AGENTS.md`「给 Agent 的提示」加一行，并**同步 `CLAUDE.md` 与 `CODEBUDDY.md`**（三份 Hub 正文一致）。

## 红线

- **不伪造验证结果**：写明验证程度（"真机待验证"、"寄存器值为推断非实测"）。元教训见 `Doc/Expe/reflection-fabricated-tool-results-2026-06-25.md`。
- **时效性声明**：寄存器值、阈值、毫秒数、文件:行号均为记录时点结论，文中注明"引用前以当前源码为准"。
- 语言：中文为主，技术名词/代码标识符保留英文原文；仓库内引用一律相对路径。
- 桌面端日志指 `%LOCALAPPDATA%\VoiceStick\VoiceStickApp.log`（不是 `%APPDATA%`）。

## 常见错误

| 错误 | 正确做法 |
|---|---|
| 不查旧文直接新建 | 先 grep 同主题，避免同一根因散落多篇孤立文档 |
| 追加时删改旧结论 | 保留历史认知演进，新节注明修正关系 |
| 写完 Expe 不同步 distilled | distilled 是 Hub 唯一经验入口，不同步等于白写 |
| 每条经验都改 Hub | 只有红线级才进 Hub，其余靠 distilled §10 速查链接 |
| 文件名忘带日期 | 日期后缀强制，便于判断时效 |
