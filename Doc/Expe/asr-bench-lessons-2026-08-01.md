# ASR 评测基准建设的成果与教训（2026-08-01）

对「构建离线 ASR 评测基准 → 基线发现 → 消融实验与修复」整个闭环的蒸馏总结。详细数据见
`asr-bench-baseline-2026-08-01.md`、`volc-config-ablation-2026-08-01.md`、
`volc-hotword-ablation-2026-08-01.md`，本文只留结论与教训。

## 成果

1. **可重复的离线 ASR 评测工具链**（`scripts/e2e_test/run_asr_bench.py` + `asr_bench/` 库 +
   `run_volc_ablation.py` + `merge_bench_results.py`）：31 条 7 类别合成语料，纯 stdlib 协议实现，
   真实凭据真实服务，产出 JSON+MD 对比报告，支持部分重跑后合并。
2. **两家 ASR 量化基线**：腾讯 CER 0.0089 / 首 partial 672ms / 尾延迟 125ms；
   火山 CER 0.0134 / 首 partial 4157ms / 尾延迟 969ms（93+92 会话，各 3 轮压力测试）。
3. **三个工具链 bug 修复**：Ogg 段表拆包、腾讯发送节奏漂移、CER 中文数字归一化。
4. **两个改变后续方向的实验结论**（见下「教训」4、5）。

## 教训

1. **ffmpeg 的 Ogg 一页多包，桌面端 OggOpusMuxer 一页一帧——抽帧必须按段表（lacing）**。
   「一页一帧」逻辑对调试音频能蒙对，对 ffmpeg 语料把整页（数 KB）当一帧，腾讯直接 4007 断连
   且表现为 SSL EOF，容易误判为网络问题。正确实现见 `asr_bench/wsproto.py::demux_ogg_packets`，
   `replay_tencent_asr.py` 已改为复用。
2. **测量工具自身的开销会污染被测指标**。腾讯 runner 每帧后 1ms 超时 recv 轮询，Windows 定时器
   粒度下实际花 10–15ms/帧，长音频发送时间被拉长 50%+，总延迟 p95 虚高 29s（真实 19s）。
   教训：发包节奏敏感路径用 select 零超时探测；指标异常先怀疑工具链再下结论（本项目目标里的
   既定循环原则，实际两次救场：4007 与 pacing 都是冒烟/小跑先暴露）。
3. **CER 对比前必须做表示形式归一**。「百分之八十」vs「80%」这类差异不归一会制造 0.22 的假
   CER，淹没真实信号。归一化顺序：先解析中文数字短语（十/百/千/万、「百分之X」），单字数字
   映射兜底；纯逐字数字串（手机号、年份）不走短语解析。
4. **火山 nonstream 二遍是双刃剑：降整体 CER，但会把第一遍正确的术语改错**（Opus→Auk 三轮
   稳定复现）。且内联热词直传与自学习平台 `boosting_table_id` 都只对第一遍生效，对二遍最终
   文本均无效（后者已用真实表 ID 实测）——二遍改错的唯一兜底是桌面端 LLM 精修。评估任何
   「热词有没有用」的实验，必须分清看的是第一遍 partial 还是二遍 final。
5. **火山首 partial 延迟 ≈ 音频全长，与 result_type/enable_nonstream/enable_ddc 无关**
   （5 组配置消融完全相同，两两差 ≤15ms）。不要再对这三个参数做重复消融；要改善流式体验
   只能换方向：换端点、换裸 PCM 格式、或向火山确认出词策略。
6. **长时间网络评测一定会遇到环境抖动**，设计上要兜底。本次全量重跑腾讯段遇本机 DNS 故障
   35 例，与 ASR 服务无关。教训：失败按类型归类（gaierror/SSL/timeout 分开统计）、支持单
   平台补跑 + 结果合并（`merge_bench_results.py`）、如实记录不掩盖——那 1 例火山真实超时
   （0.5%）反而是用户反馈「偶发不稳定」的第一条量化证据。
7. **目标拆解适合并行 swarm**：5 个修复/实验项文件互不重叠（replay 脚本/tencent.py/
   metrics.py/volcengine.py+新脚本/纯文档），5 个子代理并行一次全过，无一返工。关键是
   每项给了确切文件路径、验证命令和「只改这些文件」的边界。
