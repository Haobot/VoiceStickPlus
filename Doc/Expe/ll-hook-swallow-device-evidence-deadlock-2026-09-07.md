# LL 钩子吞键与 Raw Input 设备证据的三重死结 → keyup 后置决策模型（2026-09-07）

主题：Windows 桌面端小米遥控器按键映射（`xiaomi_keymap_*`）。背景与设计见
`Doc/Plan/xiaomi-keymap-consumer.md`，同设备采集期教训见
`Doc/Expe/xiaomi-remote-2pro-capture-and-f5-lessons-2026-09-02.md`。

## 症状（三轮真机反馈）

配置 `[xiaomi.keys] home = "Backspace"` 后：

1. v1（钩子内限时等待佐证）：按遥控器 home **不删字**，偶发"先跳回浏览器主页再恢复"。
2. v2（先吞 + 异步验证 + 超时补偿）：仍不删字，日志全是超时补偿路径。
3. v3（全局信用制 + 物理惩罚）：遥控器 home 能删字了，但**物理键盘 Home 也开始删字**，
   且 30 秒信用窗内无法恢复。

## 日志判据（真机逐键时间戳）

- **死结一（钩子内等待自阻塞）**：v1 日志 `candidate=home down wait=1`（钩子内等 raw 佐证
  超时）→ `pass-latched`（放行）→ **2ms 后** `raw vk=36` 才出现。佐证永远在钩子返回之后到达。
- **死结二（被吞按键无 MAKE raw）**：v2 日志 `candidate=home down swallow=1` 之后**无任何
  `raw vk=` 行**，最终走 `pending-compensate`（按物理键盘补偿，方向判反）；对照组放行的
  left/right 每按必有 raw 行。
- **死结三（纠正信号也被吞）**：v3 物理键盘 Home 被 keydown 时刻的信用热直接注入映射，
  该物理键的 MAKE 与 BREAK raw 均不投递（整条翻译流被吞），"物理 BREAK 到达即惩罚清信用"
  的纠错机制永远收不到信号。

## 根因

`WH_KEYBOARD_LL` 是 RIT（原始输入线程）的**同步**调用，且钩子"吞"与 Raw Input"证据"互斥：

1. 钩子回调阻塞期间，本次输入的 `WM_INPUT` 不投递——钩子内等待"本次输入的 raw"在逻辑上
   不可满足（不是时序抖动，是结构性约束）。
2. 钩子返回 1 吞掉的键不进系统翻译流，MAKE 与 BREAK 沿**双双不投递**。"先吞后验"要验的
   恰是被吞对象本身，构成悖论。
3. 任何在 keydown 时刻决策归属的设计都只能依赖先验猜测（信用/时序窗/特征比对），而 VK+扫描
   码特征无法区分"遥控器 home"与"物理键盘 Home"——物理键误判不可避免，且误判后处于无证据
   死区，无法自愈。

结论：设备归属的唯一可靠证据是**放行时刻** raw 沿自带的 `hDevice`（经
`RIDI_DEVICENAME` 接口路径解析 VID/PID）。决策必须后置到有证据的时刻。

## 修复（v4：keyup 后置决策，三次迭代的终态）

- **keydown / 按住自动重复**：一律吞（返回 1），零副作用零等待，登记 Pending
  （button/vk/scan）。映射未配置的键不进此路径，原生放行。
- **keyup（钩子内）**：**放行**。原键 down 已被吞，孤立的 up 无系统副作用（不会产生字符/
  点击），但会让该键的 BREAK 沿沿正常翻译流投递到 Raw Input——这是取证动作。
- **raw 线程**：只处理 BREAK 沿（`RI_KEY_BREAK`），识别为候选键后读 `hDevice` 判归属，
  `PostMessage`（`WM_APP+0x4D4B`）转主线程 message-only 派发窗。
- **主线程收到证据**（约 2-3ms 后）：遥控器 → `SendInput` 注入映射键 down+up 对；物理键盘
  → 补偿原键 down+up 对（vk/scan 来自 Pending）。注入带 `dwExtraInfo` 标记 + 天然
  `LLKHF_INJECTED`，自家钩子放行，无递归。
- **兜底**：keyup 放行后 200ms（`WM_TIMER` 25ms 轮询）无 BREAK（异常丢失/设备拔出）按物理
  键盘补偿；按住中的 pending 不触发兜底。
- 删除全部先验机制：关联等待窗（60/15ms）、放行闩锁、按住闩锁、全局信用、物理惩罚——
  统一由"放行取证据 + 证据后决策"取代。

## 验证（2026-09-07 真机，用户确认"测试成功"）

- 遥控器 home（映射 Backspace）：按下无反应，**松手删一个字**（决策后置的固有表现）。
- 物理键盘 Home：原生行为（跳行首），零误删。
- 遥控器 home 快速连按：各删一个字。
- CTest 全量通过（core_tests 决策状态机 v4 用例 12 项：无映射放行/pending 登记/重复吞/
  keyup 放行/BREAK 双向收尾/晚到丢弃/兜底超时/按住不触发兜底/多按钮并发/重配竞态/Reset）。

## 经验（可泛化）

1. **LL 钩子回调内永远不要等待"本次输入"的任何派生事件**——RIT 同步性意味着它们排在
   你返回之后。
2. **吞掉的键在 Raw Input 里不存在**（MAKE/BREAK 双亡）。想拿设备证据，必须放行；"先吞
   后验"范式对本场景结构性不可行。
3. **归属判定后置到有证据的时刻**，而不是在信息不全的 keydown 时刻用先验硬猜。先验方案
   的错误率也许低，但错误落在物理键盘上时用户零容忍且无法自愈。
4. **孤立 keyup 放行无害**（无对应注入 down 时系统不产生副作用）——"放行取证据"可行的
   前提，也是整个模型的关键一步。
5. 排查手法：吞/放行对照组（放行的 left/right 有 raw 行、吞掉的 home 没有）+ 逐键毫秒
   时间戳对齐，三轮就把"等待不到佐证"从现象逼成结构性结论；每轮只改一个变量。

## 遗留 / 已知取舍

- **按住连删退化为单击多次**：pending 中的自动重复一律吞、证据只在 keyup 到来。要恢复
  "按住持续删"，可在 BREAK 确认遥控器后进入"重复注入"模式（keyup 前持续注入映射 down），
  属可选增强。
- 单击反馈延迟 = 按住时长（决策在松手瞬间）。用户已接受。
- 兜底补偿后迟到的 BREAK 沿会被丢弃（pending 已消费），孤立 up 无副作用，无害。
- back 键（RC003 固件）本就不上报，与本题无关，见方案文档勘误段。
