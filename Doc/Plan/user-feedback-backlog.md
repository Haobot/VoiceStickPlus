## 2. 主题分组

### 2.1 按键映射（F4/F5）——同一代码家族，建议一轮修完

这两条不是独立小问题，而是 Windows 按键映射链路的两个确定性缺陷：

- 归属判定把**物理键盘**的同 VK 按键当成遥控器按键（F4）；
- 注入合成键时丢了**扩展键标志**（F5）。

两者都命中的键集合高度重合（方向键、回车），所以用户会同时觉得「映射后键盘坏了」且「映射出来是数字」。修复时必须一起验收，只修一个会掩盖另一个。

### 2.2 语音删除（F2/F6/F7/F8/F9）——核心是「删谁」的语义决策

现有实现的硬边界：**只删最近一次语音注入、且能通过字段/光标校验的文本**。用户实际期望显然更宽：

1. 删除目标可以是**鼠标选中的任意文本**（F7/F8），甚至是手打内容；
2. 删除粒度包含**行/段**（F2）；
3. 可删除窗口不能「悄悄过期」（F9）。

其中「删除手打文本/选区」会直接打破原方案 §1.4「不编辑用户手打内容」的非目标，属于**产品决策**，不是纯 bug 修复（见 §4 D-A）。

### 2.3 标点（F1）——先确认 ASR 是否产出词，再谈映射

`SpokenPunctuation` 已双端收录「左括号/右括号/左书名号/右书名号/破折号/左引号/右引号」，所以「不能识别」大概率不是映射表缺失，而是 ASR final 没给出这些词（引擎标点集限制，或口语被识别成近音词）。必须先采样再改代码，否则容易修错层。

### 2.4 远程桌面（F3）——先澄清拓扑，再判断是「支持边界」还是「可适配 bug」

VoiceStick 跑在哪台机器、ToDesk 往哪个方向连，决定完全不同的根因与方案。拓扑不明前不建议动代码。

## 3. 逐条记录

### F1 标点符号识别覆盖不全

- **类型**：Bug / ASR 能力边界
- **用户原话**：「目前测试标点功能 1-，。？！可以识别 （）——《 “”等不能识别」
- **现象**：自动标点只稳定产出逗号、句号、问号、叹号；括号、破折号、书名号、引号不产出。
- **现状证据**：
  - 标点独词映射双端已实现且对齐：macOS `desktop/macos/Sources/VoiceStickCore/SpokenPunctuation.swift:10-34`，映射含「左括号/右括号/左书名号/右书名号/破折号/左引号/右引号」；Windows 对应 `spoken_punctuation.cc`（测试 `core_tests_spoken_punctuation.cc`）。
  - 该能力的前提是**整轮 ASR final 恰好是一个标点名**；文本已含符号或带其他字时不转换（`SpokenPunctuation.swift:48-55`）。
  - 裸说「括号」「引号」按设计不映射（方向歧义），必须说「左括号/右括号」。
- **待验证（按顺序）**：
  1. 用 DebugAudio 同字节回放或日志，采样单独说「左括号」「右括号」「左书名号」「右书名号」「破折号」「左引号」「右引号」时的 **ASR final 原文**；
  2. 区分三种失败：① ASR 根本没配标点模型/该标点不在自动标点集；② final 是近音词（如「左扩号」）→ 同义词缺口；③ final 正确但未命中映射（代码 bug）。
- **候选方向**（采样后择一）：
  - 近音词补进映射表（双端同步 + 单测钉死）；
  - 标点名加入 ASR 热词（提升 final 命中率）；
  - `Doc/Ref/tencent-asr.md` / 火山文档确认自动标点集上限，把「引擎不支持」写进用户文档，避免误判为 bug。
- **验收口径**：单独说 8 个成对标点名（左右括号、左右书名号、左右引号、破折号），在双端各产出对应符号；说裸「括号/引号」按设计不转换且有可预期行为。
- **状态**：待复现

### F2 删除粒度缺「整行/整段」

- **类型**：需求 / 语义澄清
- **用户原话**：「删除可删除单字，整句 不能删除整行，整段。」
- **已工作（回归基线，勿破坏）**：单字（默认 1 字）、整句（最后 N 句，按 `。！？；` 与换行切分）。
- **现状证据**：
  - 动作枚举只有三个：`kDeleteLastChars` / `kDeleteLastSentences` / `kDeleteAll`（`desktop/windows/src/voice_edit_command.h:23-27`）。
  - `kDeleteAll` 的语义是「删除本次语音注入的全部」（撤销/撤回/清空/删除本次输入等白名单，`voice_edit_command.cc:57-68`），**不是**「删除光标所在整行/任意整段」。
  - 没有任何按行（`\n` 边界）或按段落（空行边界）计算的计划逻辑。
- **需澄清（§5 Q2）**：
  - 「整段」是指「本次语音输入的整段」？→ 已支持，可能是台词/提示不清；
  - 还是「光标所在/or 选中的整行、整段」？→ 新需求，与 F7/F8 的选区删除合并设计。
- **候选方向**：新增 `kDeleteLastLines` / `kDeleteCurrentLine` / `kDeleteLastParagraphs`；优先级低于选区删除（选区删除可覆盖大部分「整段」诉求）。
- **验收口径**：口述三行，说「删除上一行」只删一行；选中两段说「删除这段」只删两段；「删除本次输入」仍删除全部注入文本。
- **状态**：待澄清

### F3 ToDesk 远程 AI 机器场景不生效

- **类型**：Bug / 支持边界（拓扑待澄清）
- **用户原话**：「之前测试我们有个特殊情况 因为我们专门弄了一台ai机器 所以使用的时候都是todesk过去用的 这个场景下voicestick不能生效」
- **两种拓扑，根因完全不同**：
  - **A. VoiceStick 跑在本地机器，ToDesk 窗口连远程 AI 机器**：注入落点是本机 ToDesk 窗口。合成键（SendInput）能否被 ToDesk 转发取决于 ToDesk 的键盘转发/剪贴板同步设置及驱动过滤；剪贴板粘贴路径还依赖「远程剪贴板同步」。
  - **B. VoiceStick 跑在远程 AI 机器，用户本地用 ToDesk 连进去**：BLE 不跨远程会话，StickS3/遥控器必须与 AI 机器本机蓝牙配对（AI 机器可能无蓝牙适配器）；若已配对，注入发生在远程会话内，通常可用，但服务/会话权限、UIPI 仍可能拦截。
- **现状证据**：
  - 文本注入只有「剪贴板 + 粘贴」与按键注入两条（`Desktop/windows/src/input_injector_win.cc`），没有远程会话感知；
  - 仓库无 ToDesk/远程桌面的既有支持文档或检测逻辑（全仓 `grep todesk|远程桌面|RDP` 仅命中一处无关的 Acrylic 渲染说明）。
- **待验证**：先答 §5 Q1；再抓 `focused_app`、注入结果日志、ToDesk 设置（键盘映射、剪贴板同步）、设备连接状态。
- **候选方向**：
  - 若 A 可配置解决 → 写进用户文档（ToDesk 需开启键盘/剪贴板转发），代码侧检测前台是远程桌面窗口时给出提示；
  - 若 A 的合成键被过滤 → 评估「本地中转」不可行，明确列为不支持场景；
  - 若 B → 先解决蓝牙可达性（USB 蓝牙适配器/配对），再验证会话内注入。
- **验收口径**：在明确拓扑下，远程目标应用内完成一次语音输入 + 一次语音删除，日志可追溯注入目标。
- **状态**：待澄清

### F4 映射按键后物理键盘方向键/回车失去长按连发【P0】

- **类型**：Bug
- **用户原话**：「还有就是上一版多按键映射的版本 映射案件之后会影响键盘操作 组合检核连击无法使用 比如我映射了上下左右 我的键盘操作的时候，按住←，光标只会左移一次，无法连续左移 现在有这个问题的按键有上下左右和回车，删除没问题」
- **现象**：配置按键映射后，**物理键盘**按住方向键/回车只触发一次；松开再按才动第二次。物理 backspace 正常。
- **根因（代码层实锤，待真机日志二次确认）**：
  1. LL 键盘钩子只按 VK + scan code 反查遥控器按键：`XiaomiButtonFromVkScan(info->vkCode, info->scanCode)`（`desktop/windows/src/xiaomi_keymap_hook.cc:204`）。物理方向键/回车的 VK 与遥控器按键**完全相同**（反查特征表 `xiaomi_keymap_interceptor.cc:17-36` 含 `VK_UP/VK_DOWN/VK_LEFT/VK_RIGHT`→方向、`VK_RETURN`→ok、`VK_HOME`→home、`VK_APPS`→menu 等；可映射集合 `kXiaomiMappableButtons` 见 `desktop/windows/src/xiaomi_buttons.h:12-15`）。
  2. 映射表非空时，钩子把物理键的 keydown 与后续自动重复一律吞掉（注释明确「keydown/按住重复一律吞」，`xiaomi_keymap_hook.cc:218-221`）。
  3. keyup 放行后，`OnBreakEvidence` 判定该次不是遥控器（`from_remote=false`），走「物理键盘补偿」只注入**一次** down+up（`xiaomi_keymap_hook.cc:299-313`、`ApplyAction` :174-183）。合成键不会触发 OS 的键盘自动重复，所以光标只动一次。
  4. backspace 正常的解释：反查特征表**不含 `VK_BACK`**（`xiaomi_keymap_interceptor.cc:20-22` 注释明确「VK_BACK/0x0E 事件全部为物理键盘污染，勿收录」；遥控器「返回」是 `back`，对应 `VK_BROWSER_BACK`），所以物理 backspace 不被识别为遥控器按键，直接放行。
- **影响面**：与反查特征表同 VK 的物理键都会被误判——方向键、回车、Home、Apps（菜单）键、音量键、`` ` `` 键（`VK_OEM_3` + scan 0x29）、Sleep（罕见）。物理 backspace 与 Esc 不受影响。这会让映射功能「一开就污染正常键盘」，属阻断级。
- **候选方向**（需设计确认，不在本条直接定案）：
  - 优先用设备级识别（Raw Input 设备句柄 / HID 来源）区分物理键与遥控器键，物理键零延迟放行；
  - 在拿到 tap/HID 证据前不吞物理 keydown，只在证据到了才拦截；
  - 若保留「补偿注入」，则必须为物理键实现与 OS 一致的长按重复节拍。
- **验收口径**：
  1. 映射全部 12 个按键后，物理键盘按住方向键/回车/其他同 VK 键均连续重复，节拍与系统一致；
  2. 遥控器单击/长按行为不变（长按仍按配置节拍连发）；
  3. 组合键（Ctrl/Shift/Alt + 方向键、Ctrl+回车）在物理键盘与遥控器上都正确；
  4. 快速连击不丢键、不误注入。
- **状态**：根因已定位

### F5 方向键映射成小键盘数字【P0】

- **类型**：Bug
- **用户原话**：「另外上下左右映射出来会是小键盘的数字输入。这个倒是和susas那个bug一样」
- **现象**：把遥控器按键映射成上/下/左/右后，目标应用收到的是小键盘数字（NumLock 开启时 8/2/4/6）。
- **根因（代码层实锤）**：
  - `XiaomiKeymapHook::InjectVks` 只发 `wVk` + `MapVirtualKeyW(vk, MAPVK_VK_TO_VSC)`，`dwFlags` 仅 `KEYEVENTF_KEYUP`，**没有 `KEYEVENTF_EXTENDEDKEY`**（`desktop/windows/src/xiaomi_keymap_hook.cc:156-171`）。
  - 方向键、Home/End/PageUp/PageDown/Insert/Delete 是**扩展键**；不带扩展标志时，按下会被 Windows 解释为小键盘等价键（NumLock 开：数字；关：导航键）。这正是「映射出来是小键盘数字」的机制。
  - 同类缺陷也在 `InputInjectorWin::SendArrowDown`（`desktop/windows/src/input_injector_win.cc:146-149`，未传 `KEYEVENTF_EXTENDEDKEY`）；`wechat_input_method_hotkey.cc:104-107` 已正确处理右 Alt/右 Ctrl 的扩展标志，可作为同仓参照。
- **修复方向（明确、低风险）**：建立「扩展键 VK 集合」（或统一 `MapVirtualKeyW(vk, MAPVK_VK_TO_VSC_EX)` 并根据高位判标志），在 `InjectVks`、`SendArrowDown` 及所有按键注入原语里统一加 `KEYEVENTF_EXTENDEDKEY`；补纯逻辑/集成测试钉死每个扩展键的 flags。
- **验收口径**：
  1. NumLock 开、关两种状态下，映射方向键都产生方向键（光标移动/UI 导航），不产生数字；
  2. Home/End/PageUp/PageDown/Insert/Delete 映射同样正确；
  3. Ctrl+方向、Shift+方向等组合键正常。
- **备注**：「susas 那个 bug」在仓库内无记录（全仓 grep 无命中），若指某个外部工具/客户环境，请补充链接或复现步骤（§5 Q6）。机制上与本条一致的概率高，但不作为证据。
- **状态**：根因已定位

### F6 整句全选后删除：之前可用、后来不行

- **类型**：Bug / 回归待查（也可能是设计边界收紧）
- **用户原话**：「我之前倒是可以使用整句全选后，删除。但后来又不行了。」
- **现状证据**：
  - 双端对**非空选区**都是明确拒绝：Windows `VoiceEditRejectReason::kSelectionActive`（`voice_edit_command.h:116`、`voice_edit_command.cc:663`）；macOS `.selectionPresent`（`VoiceEditCommand.swift:516`），提示「请先取消选中」。
  - 即当前版本的**设计行为是拒绝**，不是静默失败。
- **待复现**：
  1. 确认「之前可用」的版本号（`VERSION`）与平台——是旧版无选区校验，还是当时选区读取失败走了不可验证分支；
  2. 抓当前版本的 `voice_edit` 日志，确认实际拒绝原因（`selection_active` / `text_mismatch` / `unverified`）。
- **与 F7/F8 的关系**：三条指向同一件事——用户希望「选中即目标」。应合并成一次产品决策，而不是分别打补丁。
- **验收口径**：决策后统一行为：有选区时按选区删除（若采纳），或明确提示「请先取消选中」且提示可被用户理解。
- **状态**：待复现

### F7 手打文本 + 鼠标全选提示「没有可删除的语音输入」；先语音输入几个字再全选却能删

- **类型**：Bug（行为不一致）/ 设计边界冲突
- **用户原话**：「用鼠标全选么？我测试是可以 但是有个地方 如果这段话是我打字出来的，说删除，会提示没有语音输入的内容。这时候我随便语音输入几个字，再用鼠标全选这段，就可以删除了」
- **现状证据**：
  - 删除只认「最近一次语音注入记录」：无注入记录时返回 `kEmptyTarget`（Windows `voice_edit_command.h:113`），提示文案「没有可删除的语音输入」（`localization.cc:1266`；macOS `Localization.swift:861`）。
  - 有记录 + 非空选区时，按设计应返回 `selection_active` 并提示「请先取消选中」，**不应执行删除**。
- **矛盾点（必须复现）**：用户观察到「有记录 + 全选 → 能删」。两种可能：
  1. **选区读取失败**（UIA/AX `GetSelection` 不可用或返回空），系统按「无选区」继续，随后走锚定/不可验证盲退格；盲退格在「全选」状态下会先吃掉整个选区 → 用户看到整段被删，实际执行的是盲退格，**不是选区删除**。若为真，这是安全边界漏洞：不可验证时可能删除用户手打内容。
  2. 旧版本/另一平台的行为差异。
- **验证方法**：复现时抓 `voice_edit` 日志的 `reject_reason`、`selection` 读取结果、`anchor` 命中情况与 `backspace_count`；对比「全选后删除」实际删掉的字符数是否等于选区长度。
- **需求结论（待决策）**：若期望「选中即删」，应显式支持选区删除并保证：① 只删除用户显式选中的内容；② 无选区且无注入记录时提示不变；③ 不可验证时绝不盲删非注入内容。
- **验收口径**：
  - 手打一段 + 鼠标选中 → 说「删除」→ 只删选中部分（若采纳选区语义）；
  - 手打一段 + 无选区 → 说「删除」→ 不删任何内容，提示明确；
  - 选区读取失败时日志可定位，且不会误删非注入文本。
- **状态**：待复现（含安全风险评估）

### F8 不是全选，是选择一段

- **类型**：需求
- **用户原话**：「不是全选，是选择一段」
- **解读**：用户要的是**任意局部选区**作为删除目标，而不是只能全选。这与 F6/F7 合并为「选区删除」需求：
  - 目标 = 当前选区（任意长度）；
  - 指令词可扩展「删除这段 / 删掉选中的 / 删除选中内容」；
  - 无选区时回落到现有「最近一次注入」语义。
- **现状**：无选区删除实现；`kSelectionActive` 直接拒绝。
- **验收口径**：选中句子中间任意子串，说「删除这段」→ 只删该子串；前后文本不动；选区为空时行为与今天一致。
- **状态**：待澄清（与 F6/F7 同一决策）

### F9 反复修改后「超时」，删除失效

- **类型**：体验边界（设计如此，但不可见）
- **用户原话**：「我知道后来不行了。是因为我在反复修改，后来超时了」
- **现状证据**：
  - `unverified_seconds` 默认 **8s**（范围 0~30）：`desktop/macos/Config/config.example.toml:170`、`desktop/macos/Sources/VoiceStickCore/ConfigDomain.swift:200,231`。
  - auto 模式下，字段/光标不可验证且超出该窗口 → 拒绝（不盲删）；可验证路径不受该窗口限制，靠文本锚定校验。
  - 拒绝原因是 `kUnverifiedNotAllowed` / `kTextMismatch`，但用户侧统一看到「没有可删除的语音输入」，无法区分「过期」与「无目标」。
- **结论**：不是 bug，是安全设计 + 提示粒度过粗。
- **改进方向**：
  1. 拒绝提示细分：「已超过可编辑时间窗（8s）」vs「没有可删除的语音输入」vs「光标/选区已变化」；
  2. 在注入后短暂展示「可编辑窗口」状态（overlay/托盘），让用户知道还剩多久；
  3. 对有可靠字段读取的应用，评估取消时间窗（改用文本锚定），或允许配置更长窗口；
  4. 不建议直接调大默认值而不做 1/2——误删风险随窗口线性上升。
- **验收口径**：注入 10s 后说删除 → 提示明确说明是时间窗过期；可验证应用中长时间后仍可删（若采纳 3）。
- **状态**：根因已定位

### F10 Kimi 上删除不顺利

- **类型**：Bug
- **用户原话**：「发现了一个新的bug，就是在kimi上面，用删除并不是特别的顺利。」
- **待复现信息**（§5 Q4）：
  - Kimi 桌面客户端（Electron）还是浏览器网页版（Chromium）；
  - 具体表现：无反应 / 提示无目标 / 删错位置 / 只删一部分；
  - 复现步骤与文本长度。
- **现状与技术线索**：
  - 删除链路依赖焦点字段/选区/光标读取（Windows UIA `GetSelection`，macOS AX `kAXSelectedTextRange`）；
  - Chromium 系目标（Electron/浏览器）的 AX 写入与读取存在异步生效问题（见 `Doc/Expe/targeted-replace-chromium-ax-async-write-2026-10-29.md`）；富文本编辑器（ProseMirror 类）常不暴露标准 TextPattern，导致锚定失败 → `text_mismatch` / `anchor_ambiguous` 拒绝；
  - 若光标校验失败而 verify_mode=auto 且在 8s 窗口内，可能转为盲退格 → 表现为「删不干净/删错」。
- **验证方法**：抓 `voice_edit` 全链路日志（focused_app、selection 可读性、anchor 命中、reject_reason、backspace_count），分别测长/短文本与不同光标位置。
- **候选方向**：
  - 针对 Chromium/Electron 目标做读取重试（小步轮询确认，而非一次读取定论）；
  - 富文本不可验证时明确拒绝并提示，而不是盲退格；
  - 若 Kimi 提供标准 UIA TextPattern，补一条适配与回归用例。
- **验收口径**：Kimi 中语音输入 → 说「删除」→ 连续 5 次成功（长/短文本各若干），无删错、无残留。
- **状态**：待复现

## 4. 下一步方向建议

按「修复确定性 / 用户影响 / 决策成本」排序，建议四个包：

### 包 A（立即执行，P0）：按键映射注入修复 —— F5 + F4

- **为什么先做**：F5 是明确的一行级标志缺失；F4 会让「开了映射 = 正常键盘被污染」，用户无法长期使用该功能。两者同属 `xiaomi_keymap_*` / 注入原语，一轮改完 + 一轮真机验收最省成本。
- **范围**：扩展键标志（F5）→ 物理键放行/设备级识别（F4）；顺带覆盖 `InputInjectorWin::SendArrowDown` 同类缺陷。
- **验证**：CTest 单测（flags 钉死）+ 真机四组：NumLock 开/关 × 物理键盘/遥控器；组合键；快速连击。
- **风险**：F4 涉及归属判定状态机（历史迭代多次），改动必须保留「遥控器单击/长按连发」与「BREAK 丢失兜底」的既有行为，先补测试再改。

### 包 B（P1，需产品决策）：语音删除 V2 —— F6 + F7 + F8 + F2 + F9

- **核心决策 D-A**：是否允许删除「非语音输入」的文本（鼠标选区、手打内容）。原方案明确不做（§1.4 非目标）；用户反馈明确想要。两者不能同时成立，必须拍板。
- **若采纳选区删除**，建议语义：
  1. 有选区 → 删除选区（任意长度），与是否有语音记录无关；
  2. 无选区 → 现有语义（最近一次注入，字/句/全部）；
  3. 选区读取不可用 → 拒绝并提示，**绝不盲退格**（修复 F7 的潜在误删）；
  4. 行/段粒度（F2）可选加在无选区路径上。
- **配套**：拒绝原因细分 + 可编辑窗口可见（F9）。
- **风险**：改动集中在 `VoiceEditCommand`/`VoiceTargetedEdit` 双端纯逻辑与协调器，测试基础好（双端已有大量纯逻辑用例）；主要风险是产品语义而非工程。

### 包 C（P1，先采样）：标点能力补齐 —— F1

- **第一步不是改代码**，而是 ASR final 采样（8 个标点名 × 双端/双 Provider），把失败分成「引擎不支持 / 近音词 / 映射未命中」。
- **第二步**按结论分别处理：同义词表、ASR 热词、或文档明确边界。
- **验收**：8 个标点名单说均正确；不破坏已有 `，。？！` 行为。

### 包 D（待澄清后定级）：远程桌面场景 —— F3

- 先答拓扑（§5 Q1）。若是「本机跑 VoiceStick + ToDesk 连远程」，优先尝试设置项文档化 + 前台检测提示；若是「远程机跑 VoiceStick」，优先解决蓝牙可达性。
- 在澄清前不投入开发。
