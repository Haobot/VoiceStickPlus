# 本地识别准确率提升与跨轮上下文精修方案

- 日期：2026-09-09
- 背景：真机验证本地精修过滤口水词已闭环（`Doc/Plan/local-text-refinement.md` 已交付），
  用户实测提出三个递进问题：①"鱼器渍"（=语气词）误识别是否与伪流式显示相关；
  ②本地识别准确率提升方案；③精修能否跨 3~5 轮对话用上下文推断纠正识别词。
- 状态：**M0 spike 已完成，判定 GO（跨轮纠错用 Qwen3-4B，见 §3.6 结论）**。
  M1~M4 待实施。

## 1. 问题一：伪流式与"鱼器渍"误识别无关（代码证据）

伪流式（df1feacc）的 final 生成路径（`local_asr_client_win.cc` worker 循环）：

- `final_job = is_last_received && !session_final_done`——is_last 到达**立即跳出节流等待**，
  对**当前全量 ogg_buffer**（含最后节流窗口内的尾音）执行完整重解码后才发 final。
- partial 与 final 都是"当前累计全量音频 → SenseVoice 整段前向"，**不存在增量解码的
  截断/漂移**；final 与"松键后一次性解码整段"数学等价。

**"鱼器渍"的真实成因**：yǔqìcí → yúqìzì 的同音近音混淆（三字声母韵母全同、仅声调
与一字韵腹微差），是 SenseVoice-Small **int8 量化**对低频领域词（"语气词"不在日常
高频词表头部）的固有弱点。旁证：同一条小米链路上"小米蓝牙遥控器"（更长专有名词）
识别正确——链路音质没问题，是模型词频偏置问题。

结论：**伪流式显示功能无需改动**；改进方向在文本层（见 §3），不在音频/解码层。

## 2. 问题二：本地识别准确率提升选项评估

| 方案 | 准确率收益 | 延迟/内存代价 | 风险 | 结论 |
|---|---|---|---|---|
| A. ASR 热词偏置 | 中（词汇表内） | — | **SenseVoice 不支持热词**（sherpa-onnx 热词仅 transducer；SeACo 支持但需换模型：更大、仅中文、全链路重验证） | 否决（远期再评 SeACo） |
| B. LLM 文本层纠错 | 中高（同音字/领域词，与上下文联动） | 已有 304ms/句管线复用，KV 续写后**零额外 decode** | 小模型纠错能力需 spike 验证；误改由守卫拦 | **首选**（=问题三方案） |
| C. 模型升级（int8→fp32 / 更大 ASR） | 小（量化损失 <5% 相对误判） | 内存翻倍 / 延迟破坏实时性 | 收益不匹配 | 否决 |
| D. 两级流水（快出字+后台重识别替换） | 中 | 工程复杂；注入文本跳变伤体验 | 状态机复杂度 | 否决 |

**定论**：走 B——把现有三层精修升级为"上下文感知的纠错型精修"。

## 3. 问题三：跨 3~5 轮上下文精修设计

### 3.1 需求与价值

语音输入天然是连续多轮（同一段工作口述多句）。单句"那些鱼器渍已经被过滤掉"无法
推断正词；但若上一轮说过"看看语气词有没有被过滤"，本轮同音错误即可由上下文纠正。
云端 LLM 精修（大模型）天然可带上下文，本地小模型的差距需要架构弥补。

### 3.2 核心机制：KV 续写——历史轮天然成为 few-shot 续例

当前引擎（`llama_cpp_engine.cc` Chat）每句 `llama_memory_seq_rm(seq, prefix_len, -1)`
清掉上一句，KV 里只剩 system+few-shot 前缀（~320 token）。改为：

```
KV 序列 = [system+few-shot 前缀] [轮1 user][轮1 assistant] [轮2 user][轮2 assistant]
          ... [轮N-1 user][轮N-1 assistant] [轮N user] → 生成轮N assistant
```

- **每轮完成后不清 KV**，下一句从上轮末尾续写（prefix_len 动态推进为上轮末位置）。
- 历史轮在模型眼里就是 few-shot 的延续（同构"输入：/输出："对），**不改变 few-shot
  任务形态**——这对只会模仿示例、不会跟随指令的小模型是关键（0.6B 教训）。
- **性能**：历史 token 已 decode 过，零额外推理；稳态延迟维持 ~304ms/句。
  （对比"prompt 里重复历史"方案：每句要多 decode 5×~150 token，慢 2~3 倍，否决。）
- **上下文预算**：320 + 5×~150 + 512(当句) + 256(生成) ≈ 1838 < kCtxTokens 2048，
  Qwen3-1.7B 原生 32k 上下文，2048 是我们自设预算，充裕。
- **滑窗**：超 5 轮或超预算 → 简化为**全量重建**（清 KV → 重 decode 前缀 + 保留的
  最近 4~5 轮文本），一次性 ~1.2s、每 5 轮才发生一次，可接受；不做 KV 中段删除+
  位置平移（`llama_memory_seq_add` 路径正确性风险高，收益小）。

### 3.3 纠错通道与分级守卫

现状守卫 `RefineResultSafe` 禁止任何新增/改写字符——同音纠错（鱼→语、器→气、渍→词）
必被拦。新增**同音改写守卫通道**，与现行纯删除守卫并行：

```
LLM 输出 → 纯删除？→ 现行守卫放行
        → 含改写？→ 同音守卫：逐字比对拼音（改写字符须与原字符同音或近音：
                    声韵母全同允许声调不同；或命中模糊音对表 zh/z ch/sh c/s
                    n/l in/ing an/ang 等）+ 改写字数 ≤ 原文 30%
                  → 通过：放行纠正版
                  → 不通过：回退「纯删除精修结果」（不回退原文，仍保底过滤口水词）
```

- **拼音表**：常用 ~3.5k 汉字 → 拼音数组（含多音字全读音），const 数组编译进
  `text_refiner`（约 100KB 量级），无运行时依赖。
- few-shot 示例新增 2~3 组跨轮纠错样例（历史轮建立词汇 → 当轮同音错误 → 纠正输出），
  含"鱼器渍→语气词"真实案例。
- **默认关闭**：`[local_asr] refine_cross_turn = false`——改写能力先以设置开关观察，
  稳定后再考虑默认开（对齐项目"守卫保底不劣化"原则）。

### 3.4 历史缓冲（协调器）

- 全局单一环形缓冲 5 轮 `{raw_asr, refined}`（跨设备共享上下文：同一用户连续口述，
  设备切换语义连续；per-device 隔离收益小复杂度高）。
- 过期：2 分钟无新会话轮即清空（陈旧上下文反而误导）。
- 会话取消/失败不进历史；守卫拦截的回退结果进历史（refined 字段记规则级结果）。

### 3.5 TDD 切分（红-绿-重构，逐层可合入）

1. **拼音守卫纯函数**：同音/近音/模糊音判定矩阵（正例：鱼语同音 yu、渍词近音 zi/ci
   模糊；负例：删半句、换实义词）——单测全覆盖。
2. **历史缓冲**：滑窗 5 轮、2 分钟过期、清空、取消不入历史。
3. **引擎 KV 续写**：prefix_len 动态推进 / 滑窗重建路径；FakeEngine 语义测试 +
   真模型多轮 smoke（断言第 2~5 句延迟不高于现基线 + 上下文可见性）。
4. **client 编排**：历史传入、纠错输出分流（纯删除 vs 改写走对应守卫）、诊断日志
   扩展（`correct '鱼器渍'->'语气词'` 归因行）。
5. **协调器接线 + 设置开关**（复选框「跨轮上下文纠错」）+ 文档。

### 3.6 M0 spike（go/no-go 门，先行）——已完成，判定 **GO（换 4B）**

> 结论（2026-09-09，报告：m0/refine/report_cross_turn.md 与 report_cross_turn_4b.md）：
> - **1.7B 终判 NO-GO**：三种 prompt 形态全试——生成+教学（1/5，字面复读无泛化）、
>   「上文：」显式通道（1/5）、纠正指令模式（2/6=33%）——均 <60%。失败形态：漏检输出
>   「无」、目标词选错（口头鱼→口水词）、格式逃逸回生成模式、把指令模板本身当输出。
> - **4B（Qwen3-4B-Q4_K_M）终判 GO**：同评测集同教学同守卫口径，纠正指令模式
>   4/6=67%（≥60%）+ 负例 2/2=100%。检测召回实为 6/6（correct 类指令全部正确或
>   合理，无格式逃逸），3 例 miss 全部为守卫/评测集侧拒绝（见报告归因表）。
> - 守卫修正：FUZZY_FINALS 补 ("e","i")（卷舌韵母弱化：设/识、这/之、车/吃），
>   补后 C08 翻正且负例仍全拦。
> - 生产模型决策：**跨轮纠错用 4B，纯删除口水词档维持 1.7B 可选**；4B 代价
>   （内存 +1.4GB 常驻、单句粗估 600~800ms）M2 常驻引擎实测为准，超 1.5s/句或
>   内存不可接受时回报用户再决策。

原 spike 设计（留档）：

- m0/refine 扩展多轮评测集：5~8 组"前轮建立词汇 → 当轮同音错误"样本（含真机
  "鱼器渍→语气词"案例、上轮提"蓝牙遥控器"本轮误识别等）。
- 脚本模拟 KV 续写（多轮 Chat 复用同一引擎实例，历史留在上下文）跑评测。
- **通过标准**：纠错命中 ≥60% 且全部误改样例被拼音守卫拦下 → 立项 M1。
- **不通过备选**：①升 Qwen3-4B-Q4_K_M（~2.5GB，加载 ~2s、单句 ~700ms 需重测预算，
  常驻内存 +1.4GB）；②降级目标——跨轮上下文只用于提升"删除类"精修（如据上文判断
  "那个"是否口头语），不做改写纠错（守卫零改动，风险最低）。
