## 1. 排序原则

1. **先消除会反复咬人的稳定性问题** —— 今天的排查成本几乎全来自「静默失效 + 复现路径不确定」。
   不先收敛它，后面每做一次联调都要重付一次代价。
2. **再做用户明确要的 Phase 3 切换器**（StickS3 作为唯一枢纽切目标）。
3. **补验收** —— 已交付但没真机验收的功能不算完成（P1 按键映射、macOS）。
4. **最后技术债与发布**。

## 2. 阶段

### P0 — 僵尸会话自愈（约 1-2 天）★ 最高优先

**问题**：设备重启 → LTK 轮换 → WinRT 缓存的加密上下文失效 → CCCD 订阅与写入全部「假成功」
（设备侧 `state_sub=0`）⇒ `voice_ble_is_ready()` 恒假、录音被拒 ⇒ 语音静默失效；
且此时设备已被系统 HID 宿主连上并停止广播，app 重扫永远等不到。

**现状**：能识别 + 弹气泡指引，但**仍需用户手动到系统设置重配一次**。

**目标**：无需用户干预即可恢复；**且自愈失败时不得破坏当前可用的 HOGP 按键直通**。

**候选动作序列（待定案，见 §3.1）**：
- A. 仅回收 WinRT 侧对象（`Close BluetoothLEDevice` + `GattSession`）后重连 —— 最轻，未知能否清掉 OS 层缓存
- B. 复用现有恢复路径全量（unpair + radio reset + `PairAsync` 重建）—— 最彻底，代价是一次全链路中断且失败会弄坏按键
- C. 先 A，A 无效再退 B（**倾向推荐**，需真机验证 A 是否够）

**验收**：设备重启后，不改任何系统设置，app 在约定时限内自行回到 `stage=ready` 且 `state notify` 恢复流动；
连续 N 次重启无人工干预。**注意**：设备重启本身仍会产生新 LTK，这是 BLE 加密的固有行为，
本阶段只解决「app 能否自愈」，不解决「LTK 为何轮换」。

**风险**：A 无效 → 回到 B 的全链路中断代价；需在真机上量出 A 的成功率再决定默认策略。

### P1 — Phase 3 切换器（约 3-5 天）

**目标**：StickS3 作为唯一枢纽，遥控器只与它配对，由它在多个目标（Win / Mac）之间切换按键与语音的去向。

**现状核实**：`gateway_switcher` **零实现**；但底座已就位 —— `MAX_BONDS=6` / `MAX_CONNECTIONS=3` 已按 §5.1 调整。

**交付物**：
1. 目标表（NVS 持久化 {名称, 主机地址, 类型}，上限 4）
2. `gateway_switcher` 纯逻辑状态机（host 单测，沿用 §7 TDD 纪律）
3. LVGL 菜单 + 编码器交互（唤起 / 选择 / 确认）
4. 屏幕状态显示（「已连接：<目标>」）

**已由今天真机结论澄清的机制**（避免重新踩）：
- 切换 = 断开当前目标 → `s_connected=false` → 现有看门狗自动重开广播 → 新目标凭心跳/扫描重连。**不需要新造广播机制**。
- **小米链路（central 侧）与目标链路（peripheral 侧）互不干扰**，切换期间保持不断。
- 切换后目标侧 app 存在僵尸风险 → **依赖 P0**。这是 P0 排在前面的直接原因。

**验收**：切换 ≤2s（§5.5 预算）；切换后新目标上语音与按键均可用；切换期间小米链路零断开；
多目标来回切换 ≥10 次稳定。

### P2 — macOS 端网关适配（约 2-4 天，可与 P1 并行）

**现状核实**：`desktop/macos` 里**网关相关代码为零** —— 麦克风音频归一化在固件侧完成，
所以理论上音频/状态通道零改动，但下面两项缺失。

**交付物**：
1. `gateway_key` 事件解析（软件路由键）—— 现状 macOS 端会静默忽略
2. HOGP 按键直通的系统配对引导 —— **macOS 无 Windows 式 `PairAsync`**，
   需先 spike：能否用 CoreBluetooth 访问受保护特征拉起配对，还是只能引导用户在系统设置里添加为键盘
3. 语音链路真机验证（预期零改动，但必须实测）

**验收**：Mac 上语音、按键直通、软件路由键三项均可用；配对引导不给用户制造「配两遍」的新负担。

### P3 — 验收补齐（约 1-2 天）

| 项 | 现状 | 验收口径 |
|---|---|---|
| P1 按键自定义 | 代码已交付（Windows 有 `kMenuXiaomiKeymap` 对话框 + `gateway_keymap_set/get` 协议，固件侧已接线） | 对话框配动作 → 软件路由 → 桌面端注入，逐键实测 |
| macOS 语音端到端 | 未测 | 与 Windows 同口径 |
| 时延增量 | 未测 | §5.6：总增量 ≤80ms（分段实测：小米→Stick、固件处理、Stick→目标） |

### P4 — 技术债与发布（约 1-2 天）

| 项 | 说明 |
|---|---|
| `CONFIG_BT_NIMBLE_LOG_LEVEL` | 现为 DEBUG，是 2026-06-28 `81c37c6b` 的既有设置（非本次调试引入）；是否回 WARNING 待定 |
| `start_ext` 失败步骤标签 | 失败点位于 `"opus"` 赋值之前，屏幕显示 `Audio wait:…` 有误导；一行改 |

## 3. 待定案决策点

1. **P0 的自愈力度**：A / B / C（§2-P0）—— 建议先花半天真机量 A 的成功率再定。
2. **P1 的切换交互**：编码器菜单的具体形态（长按唤起？旋转选择？确认键？）与目标数上限（默认 4）。
3. **P2 是否本期排期**：Mac 是硬需求还是可以先只支持 Windows。
4. **P4 的 OTA 取舍**：定位网关模式 OTA 断链，还是明确网关模式只走串口升级。

## 4. 依赖关系

```
P0（僵尸自愈）──┬─→ P1（切换器；切换后 app 重连依赖 P0）
                └─→ P2（macOS；同样依赖会话可靠性）
P1 与 P2 可并行；P3 依赖 P1/P2 的产物；P4 独立，可随时插入。
```

## 5. 阶段性风险

- **P0 的 A 方案可能无效**：WinRT 的加密上下文缓存层级不在应用可控范围（现有代码注释已指出 BTHLE 驱动
  在 controller 级别另有 key cache）。若 A 无效，只能在「全链路中断一次」与「等待用户手动重配」之间取舍。
- **P1 的多目标**：每个目标都需要一次系统级配对（BLE HID 固有），目标数增加会放大配对与 LTK 轮换的复杂度。
- **P2 的 macOS 配对**：macOS 没有等价于 `PairAsync` 的公开 API，最坏情况只能引导用户手动添加键盘，
  这会削弱本计划在 Windows 上刚达成的「一站式配对」体验 —— 需在 spike 后决定话术。
